# GAMP Specs Design Summary

## Introduction

This skill defines how a project creates and maintains its README, HTML documentation, agent guidance, design specifications (DS files), and coding-style reference. It preserves the former `gamp-structure` behavior and adds synchronization rules for repositories that contain a catalog of skills.

## Core Content

The skill ties `README.md`, `AGENTS.md`, `docs/`, and `docs/specs/` together. It requires README instructions that let a new user install, configure, start, integrate, or use the project through every path that applies. Across all documents, it requires concrete language, verified terminology, a reading order that introduces concepts coherently, and feature descriptions that explain purpose before implementation. Documentation-generation and documentation-review skills are internal authoring tools and must not appear in persistent project documentation merely because they were used; a skill is documented only when the target repository implements, distributes, or exposes it as product functionality, and authoring provenance remains prohibited. The documentation contains one canonical terminology page at `docs/wiki.html` and no page-local `Definitions` sections. Every project-specific term, acronym, named component, and architectural concept has one stable wiki anchor and a detailed, evidence-backed explanation of its meaning, purpose, users or owners, behavior, relationships, and confirmed boundaries or limitations. Eligible term occurrences in HTML documentation and DS content link to the exact canonical wiki anchor, while page titles and section headings remain unlinked and useful inline context may remain. Documentation and DS prose blocks remain unwrapped in their source files, use the full available width of their own containing boxes, and wrap naturally only at the box boundary without manual or artificially early line breaks or artificial width constraints. Documentation must represent the final product contract rather than the repository's intermediate development state: user-facing pages must not report missing code, unfinished work, or “planned” interfaces. DS files use only `Introduction` and `Core Content`, with no `Conclusion` section. They express requirements, rationale, limitations, assumptions, alternatives, and contract boundaries as declarative statements in `Core Content`; their frontmatter contains exactly `title` and `summary`, `title` equals the filename stem, and the identifier is derived from that filename. They contain no separate `ID`, `Status`, or `Owner` fields, sections, labels, badges, or metadata blocks. Every project receives `DS003-main-behavior.md`, whose accepted components come from `detect-main-behaviors` and cover supported user-impacting business behavior, major hidden functional behavior, project-special behavior, primary paths, project-spanning behavior, essential interfaces, active direction-changing consequences, and architectural skeleton. DS003 gives every accepted component its own `###` chapter inside `Core Content` and begins that section with an exactly two-column `Name` and `Explanation` summary table when multiple components exist. Any DS003 table has no more than two columns. DS003 names concrete actors, commands, routes, environment variables, paths, lifecycle actions, profiles, and other interfaces when they affect users or integrations; it explains their behavior with direct verbs and plain language while omitting private code mechanics without a major consequence. The generated specification matrix contains only the linked `DS0xx-description` name and a short description; it contains no title, status, owner, or auxiliary columns. Comparisons must identify a practical difference between real alternatives; they must not decorate a direct statement with an obviously undesirable alternative. HTML documentation must use the available page width without a fixed maximum-width constraint on the main text panel, with compact responsive padding around and inside that panel. Its header is the single primary navigation system, every top-level header control is a submenu button, and every destination appears inside exactly one subject-based submenu. Direct top-level header links are prohibited. `Specifications` and `Wiki` are submenu entries that link respectively to the matrix and `wiki.html`; a one-item submenu is permitted only when its subject has no other valid destination. Diagram guidance is centralized in a dedicated reference and requires one centered italic caption below each unframed diagram, meaningful containment of related actors, a limited actor count, and consistent category-based colors and typography. The skill also defines three-digit DS names, required numbering, English persistent content, diagram assets under `docs/assets/`, and declarative DS contracts.

Every generated `docs/index.html` must contain a Documentation Map after the project overview unless the target project has an explicitly documented small-scope exception. The map is one responsive, column-oriented semantic table that mirrors the primary header navigation exactly. Each `<th scope="col">` uses the exact text and order of one top-level submenu button and is a group heading rather than a link. The cells below reproduce that submenu's destinations in order; every non-empty cell contains one real link with the same label and target followed immediately by a concise, evidence-backed description of what the page represents. Every header destination appears exactly once, no destination absent from the header is added, and individual DS or specification files remain behind the single specification entry unless they are explicit header links. Menus of different lengths use visually empty non-interactive alignment cells. The table remains visually open instead of using a rigid spreadsheet grid, and concise prose below it explains a recommended reading flow using actual group and page names.

When a target project uses WebSkel, GAMP guidance must require `webskel-ui-engineering` and carry its verified coding rules into `DS001-coding-style.md`. The target documentation must give WebSkel-specific terms detailed, verified entries on `docs/wiki.html` and link eligible occurrences to their exact canonical anchors.
Future project bootstraps must use this skill as the starting point for repository documentation rules. Changes to project layout, DS policy, coding-style rules, reader onboarding, or documentation synchronization must be reflected here first.

When `node-coding-style` is available, GAMP incorporates its default Node.js `.mjs` and dependency rules into the project's DS001 and agent guidance while preserving explicit overrides. The integration remains optional and does not add a required skill dependency. It carries local `dependencies.md` records, elimination-first dependency choices, pinned project-local or skill-local `external/` source, license and update information, authorized environment exceptions, startup checks, and the question before converting existing Python skills. Consumer documentation describes the host's effective rules; imported skills retain their own records inside their folders.
