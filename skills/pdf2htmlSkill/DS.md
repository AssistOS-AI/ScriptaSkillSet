# PDF to Semantic HTML Design Summary

## Introduction

The `pdf2html` skill converts born-digital PDF documents into responsive semantic HTML folders. It prioritizes document hierarchy, reading order, native tables, local figures, and broadly faithful typography over fixed coordinates or pixel-identical page reproduction.

## Core Content

The conversion pipeline validates the immutable source, rejects encrypted input, and processes the document locally with Docling. Optical character recognition and picture description are disabled. A picture containing words remains a picture; its pixels are not promoted into headings, paragraphs, or other HTML text.

Docling supplies reading order, semantic item classification, picture regions, table structure, and page provenance. The HTML serializer retains native table spans and referenced picture assets. Pdfplumber supplies independent source text, source lines, drawing geometry, and occurrence-level typography observations used to derive body size, generic font family, heading scale, text color, exact bold, italic, or materially different block-size occurrences, and repeated body-paragraph first-line offsets. Pypdf supplies URI annotations and resolvable internal destinations. The renderer removes serializer-inferred inline emphasis before applying only aligned source evidence, applies block font size independently of Docling classification, demotes headings unsupported by source font size, and creates one stable anchor per PDF page. Materially different font sizes are emitted as ratios of a shared `--pdf-reader-size` base rather than absolute values. Each source-page section resolves that base from a host `--reader-font-size`, a local `--standalone-size`, or the PDF body size, in that order, so extraction into a host reader preserves proportional A−/A+ scaling. An inline, self-contained message bridge applies `axiologic-reader-settings` when the generated page is loaded through a local iframe. Normal browser output renders every source page as a separate responsive white sheet using its physical aspect ratio and source-derived margins, so intentional blank page area remains visible; each sheet also has a compact gap, subtle shadow, and numbered footer. Paragraphs use book-style justification, and only paragraphs whose aligned first source line matches a document-wide repeated indent receive `text-indent`, including short one-line paragraphs. Source-derived display spacing is applied only between adjacent centered flow blocks, preventing a later centered notice from becoming artificial whitespace after a heading across intervening prose. Table fills and individual horizontal or vertical cell borders follow aligned source rectangles and strokes; table widths and margins are clamped to the responsive content box so sub-pixel extraction differences do not create false overflow. Inferred centering requires every aligned source line to be geometrically centered and excludes ordinary paragraphs beginning on repeated body-text indents, preventing short justified lines from being mistaken for centered display text; uppercase display blocks may exceed the compact-caption width threshold. Explicit fixed page height and hard page breaks apply only to print CSS. A merged one-column table is split only when consecutive PDF lines reproduce its normalized content exactly; linked contents tables are rendered as borderless typographic rows with flexible dotted leaders and right-aligned page numbers. Pdfplumber also locates embedded-image occurrences omitted by Docling; those regions are rendered and restored on their source page without text interpretation. Generated CSS combines source-derived typography with restrained reader presentation and structural responsive behavior.

Every conversion includes deterministic quality assurance. Source and output tokens are compared for coverage and local ordering. The page-anchor set must match every source PDF page. Structural checks require each expected table and picture to survive serialization. Asset checks reject missing, invalid, zero-sized, or remote images. Chromium renders the document at three viewport widths and rejects broken images, console errors, and global horizontal overflow. Poppler renders representative source pages for an informational visual comparison whose score does not gate semantic output.

Successful conversion is staged before publication. The generated book consists only of `index.html` and its local `assets/`; validation and conversion metadata are returned to the caller instead of being bundled with the reader artifact. Persistent QA is opt-in and stored in a hidden internal path. A populated destination is never replaced implicitly, and explicit overwrite is permitted only when the generator marker in `index.html` proves ownership by this tool; legacy manifest ownership remains supported for migration. Failed validation retains diagnostic output in a sibling directory and never publishes it as successful output.

In-place conversion defaults to `book.pdf` in the invocation directory and publishes `index.html` plus `assets/` beside the immutable source. Batch conversion accepts files and recursively discovered PDFs, infers supported language codes from parent folders or filename suffixes, and publishes each result beside its source. It rejects multiple PDFs targeting the same folder. Publication changes only converter-owned `index.html` and `assets/`, preserving every unrelated file.

The first version does not preserve interactive forms, signatures, PDF JavaScript, audio, video, encryption, or exact proprietary font files. It does not use a remote API, LLM, OCR engine, or hidden host-project source dependency.

## Decisions & Questions

### Question #1: Why does visual similarity not determine pass or failure?

Response: A PDF fixes content to page coordinates while semantic HTML reflows content for different viewports. Visual comparison remains useful diagnostic evidence, but content, structure, assets, and browser integrity define correctness.

## Conclusion

The portable unit is the complete repository root. Its descriptor, implementation, references, dependency lock, tests, and output contract must remain synchronized. A POSIX launcher rooted beside `SKILL.md` owns the per-skill `.venv`, provisions native Python and Chromium on first use, and executes every command without importing a host-project environment. The launcher is also the single sandbox permission boundary: bootstrap, browser installation, runtime verification, conversion, and validation remain descendants of one approved command. Host Poppler and `uv` are detected prerequisites rather than hidden global mutations.
